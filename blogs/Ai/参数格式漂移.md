# 在 Agent 系统中如何解决这类问题

这是 Agent 系统里非常常见的"**参数格式漂移**"问题。可以从**程序侧（工具/框架）**和**模型侧**两方面解决，且**程序完全可以做容错处理**。下面分层说明。

---

## 一、根本原因回顾

LLM 生成工具调用参数时，本质是在"生成文本"，无法 100% 保证类型一致。常见漂移：
- 数组/对象被序列化成字符串（本例）
- 字段名大小写/命名风格错误（`Status` vs `status`）
- 数字被写成字符串 `"1"` vs `1`
- 布尔值 `"true"` vs `true`
- 转义层数不对

---

## 二、程序侧解决方案（最有效，推荐）

### 1. 入参归一化（Normalization Layer）—— 最实用

在工具执行前加一层"参数清洗"，容忍常见漂移：

```python
def normalize_todos(todos):
    # 容错1：如果是字符串，尝试反序列化
    if isinstance(todos, str):
        try:
            todos = json.loads(todos)
        except json.JSONDecodeError:
            raise ToolInputError("todos 无法解析为数组")

    # 容错2：确保是 list
    if not isinstance(todos, list):
        raise ToolInputError("todos 必须是数组")

    # 容错3：字段名归一化（大小写/别名）
    normalized = []
    for item in todos:
        if isinstance(item, str):   # 防止遍历到字符
            raise ToolInputError("每个 todo 必须是对象")
        item = {k.lower(): v for k, v in item.items()}
        normalized.append({
            "content": item.get("content"),
            "status": item.get("status", "pending"),
        })
    return normalized
```

> 本例中 `dxf_open_with_context` 之所以成功，正是因为它内部对 `params`（字符串）做了 `json.loads`，而 `todo_write` 没做。**只要给 `todo_write` 加上同样的归一化，两次失败都能自动救回。**

### 2. Schema 校验 + 强制约束（JSON Schema / Pydantic）

用严格 schema 定义工具参数，并开启 **strict function calling**（OpenAI / Claude 都支持）：

```python
class Todo(BaseModel):
    content: str
    status: Literal["pending", "in_progress", "completed"]

class TodoWriteArgs(BaseModel):
    todos: List[Todo]
```

- 现代模型 API 支持 `strict: true` / `structured outputs`，能**在生成阶段就强制类型**，从源头减少漂移。
- Pydantic 还能配合 `model_config` 做大小写不敏感、别名映射。

### 3. 结构化错误反馈 + 自动重试（Reflexion / 自愈）

关键：**报错信息要能指导模型改对**。本例的报错很糟糕：
```
error: 'str' object has no attribute 'get'
```
模型看不懂，于是瞎改成了 `Status`。改进后应该是：

```
参数错误：todos 应为数组对象，但收到了字符串。
请直接传入 JSON 数组，不要序列化成字符串。
正确示例：{"todos": [{"content": "...", "status": "pending"}]}
```

配合框架层的**自动重试循环**：
```
调用 → 校验失败 → 把结构化错误 + 正确示例喂回模型 → 重试（限 2~3 次）
```
大多数漂移能在第一次重试内被纠正。

### 4. 工具网关统一拦截

在 Agent 框架（如 LangGraph / 自研）里做一个**通用 middleware**，对所有工具统一处理：
- 字符串型 JSON 自动尝试 `json.loads`
- 记录漂移日志用于监控
- 归一化后再分发给具体工具

---

## 三、模型侧优化

| 手段                                 | 说明                                          |
| ------------------------------------ | --------------------------------------------- |
| **Structured Outputs / strict 模式** | 从生成端约束类型，最根本                      |
| **Few-shot 示例**                    | 在工具描述里给一个正确调用示例                |
| **清晰的参数描述**                   | 明确写 "todos is an array, NOT a JSON string" |
| **降低温度**                         | 减少格式随机性                                |

---

## 四、程序能做到什么程度？

**能做到自动兜底，但不能保证 100%。** 分层能力：

| 层级               | 能否自动解决本例 | 说明                                            |
| ------------------ | :--------------: | ----------------------------------------------- |
| 入参归一化         |       ✅ 能       | 字符串自动 parse + 字段名归一化，两次失败都能救 |
| Schema strict 模式 |    ✅ 大概率能    | 生成阶段就避免漂移                              |
| 结构化错误 + 重试  |       ✅ 能       | 引导模型自己改对                                |
| 完全不做处理       |        ❌         | 就是本例的结果                                  |

**推荐组合拳（工程最佳实践）**：

```
① 生成端：strict/structured output 减少漂移
        ↓
② 执行前：归一化层（字符串自动 parse + 字段归一化）
        ↓
③ 校验失败：返回带正确示例的结构化错误
        ↓
④ Agent 循环：自动重试 2~3 次
        ↓
⑤ 仍失败：降级（跳过非关键步骤 / 上报人工）
```

---

## 五、针对本案例的具体建议

1. **给 `todo_write` 加归一化**：像 `dxf_open_with_context` 那样，检测到 `todos` 是字符串就 `json.loads`。这一步就能彻底修复。
2. **字段名做小写归一化**：兼容 `Status`/`status`。
3. **改善报错文案**：把 `'str' object has no attribute 'get'` 换成人话 + 正确示例。
4. **加自动重试**：让模型有机会自我纠正。
5. **降级策略**：注意到 AI 最后主动"跳过 TODO 更新继续主任务"——这其实是一个不错的降级行为，可以把它设计成显式策略（非关键工具失败不阻断主流程）。

---

**一句话总结**：这类参数漂移在 Agent 系统里应当**默认它会发生**，程序侧通过「归一化兜底 + 严格 schema + 结构化错误引导 + 自动重试 + 优雅降级」的组合来解决，其中最立竿见影的就是给工具加一个入参归一化层——本例只要 `todo_write` 也做 `json.loads` 兜底，就完全不会失败。
